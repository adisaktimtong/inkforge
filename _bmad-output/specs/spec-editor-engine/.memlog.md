- (topic) In-house, headless rich-text editor engine for React and Next.js CMS page content.
- (direction) Replace paid TinyMCE usage because product-specific customization has been difficult; flexibility is the primary driver rather than license cost alone.
- (decision) Existing CMS content remains HTML at the system boundary and is part of a page rather than an independently published article.
- (decision) The editor uses a structured document model internally and parses HTML on load and serializes HTML on save.
- (decision) The engine is headless and framework-independent; React and Next.js support is delivered through an adapter.
- (decision) Extensibility is plugin-first, covering nodes, marks, commands, keymaps, parsing, serialization, and UI composition.
- (constraint) Plugins dispatch commands and transactions and cannot mutate internal editor state directly.
- (constraint) The editor UI runs client-side in Next.js; saved, sanitized HTML can be rendered server-side without shipping the editor bundle.
- (constraint) Server-side HTML sanitization remains mandatory; the editor is not a security boundary.
- (capability) CAP-1: Import existing HTML into an editable structured document and export semantically equivalent HTML without losing supported content.
- (capability) CAP-2: Author the CMS MVP formatting set: paragraphs, headings, quotes, lists, inline marks, links, images, and code blocks.
- (capability) CAP-3: Extend content and behavior through plugins without modifying editor core.
- (capability) CAP-4: Integrate as a reusable form field in React applications while the parent form owns persistence.
- (capability) CAP-5: Operate in Next.js client boundaries while allowing server-rendered output HTML.
- (capability) CAP-6: Compose and theme toolbar UI independently from the headless engine.
- (capability) CAP-7: Preserve editing correctness across selection, keyboard commands, undo/redo, clipboard input, and IME composition including Thai text.
- (capability) CAP-8: Insert and edit images through an application-supplied upload integration with alt text support.
- (capability) CAP-9: Detect dirty state and expose deterministic HTML through change and imperative APIs for the containing page form.
- (non-goal) MVP does not target full TinyMCE feature parity, real-time collaboration, track changes, tables, video embeds, raw HTML source editing, or block drag-and-drop.
- (non-goal) Exact byte-for-byte preservation of arbitrary HTML, attribute ordering, and whitespace is not required; semantic preservation of the supported subset is required.
- (assumption) MVP is desktop-first and targets current evergreen browsers; the precise browser and mobile support matrix remains open.
- (assumption) Existing TinyMCE content primarily uses the MVP-supported HTML subset; production fixtures are needed to verify this.
- (question) Which browsers, minimum versions, and mobile editing environments are required?
- (question) How should unsupported legacy HTML be handled: unwrap, reject, or preserve as a sanitized read-only node?
- (question) Does existing content contain tables, media embeds, inline styles, or custom TinyMCE markup that must round-trip in MVP?
- (question) What image upload API and asset metadata contract must CAP-8 implement?
- (question) What accessibility conformance target is required?

- (event) Coherence validation passed: every capability has an intent and demonstrable success criterion; constraints, non-goals, assumptions, and open questions are explicit.

- (event) การตรวจ coherence หลังแปลผ่าน: CAP-1 ถึง CAP-9 มีเจตนาและเกณฑ์สำเร็จครบ ข้อจำกัด สิ่งที่ไม่อยู่ในขอบเขต สมมติฐาน และคำถามเปิดยังคงชัดเจน
- (event) การตรวจ preservation หลังแปลผ่าน: ข้อกำหนด HTML, plugin-first architecture, React/Next.js boundary, Thai IME และ TinyMCE compatibility ยังคงอยู่ครบในเอกสารภาษาไทย
- (direction) Use case เดิมต้องรองรับสีข้อความ สีพื้นหลังข้อความ สีพื้นหลัง ขนาดตัวอักษร รูปแบบตัวอักษร และเมนูที่ consumer ปรับแต่งหรือเพิ่มปุ่มเปิด modal ได้
- (capability) CAP-2 ขยายให้ครอบคลุม text color, text highlight, block background, font size และ font family โดยใช้ค่าที่ consumer กำหนด
- (capability) CAP-6 ขยายให้ consumer จัดองค์ประกอบเมนูและเพิ่ม custom action ที่เปิด UI เช่น modal แล้ว dispatch command ที่ลงทะเบียนไว้ได้โดยไม่แก้ core
- (decision) ค่า style ต้องมาจาก allowlist/configuration ของ consumer และ serializer ส่งออกเฉพาะ CSS property กับค่าที่อนุญาต
- (assumption) รายการ “กำหนดรูปแบบฟ้อน” ที่ปรากฏซ้ำหมายถึง font family use case เดียวกัน
- (assumption) “สีพื้นหลังฟ้อน” หมายถึง text highlight และ “สีพื้นหลัง” หมายถึงพื้นหลังระดับ block; ผู้ใช้ยังต้องยืนยันความหมายนี้
- (question) สีพื้นหลังต้องใช้กับ block ที่เลือกหรือพื้นหลังของพื้นที่ editor ทั้งหมด?
- (event) การตรวจ coherence หลังเพิ่ม use case ผ่าน: CAP-2 และ CAP-6 มีเกณฑ์ตรวจรับที่ครอบคลุม style และ custom menu โดย capability ID เดิมไม่เปลี่ยน
- (event) การตรวจ preservation หลังเพิ่ม use case ผ่าน: color, highlight, block background, font size, font family, consumer menu และ modal action อยู่ครบใน SPEC.md, html-contract.md และ customization.md
- (decision) Typography, color, font และ background ใช้ design token ที่ consumer กำหนด ผู้เขียนไม่ป้อน CSS value อิสระ
- (decision) Responsive typography เก็บ semantic token ID ใน document model และให้ content CSS กำหนดค่าที่ต่างกันระหว่าง mobile/desktop รวมถึง line-height
- (decision) Presentation token serialize เป็น stable namespaced class เช่น `rte-typo-lead` แทน inline style หรือ `data-rte-typography`; class เหล่านี้เป็น public HTML contract และห้าม hash
- (decision) `data-*` ใช้เฉพาะ metadata เชิงโครงสร้างของ custom node ส่วน semantic meaning ใช้ HTML element และ presentation ใช้ token class
- (capability) CAP-5 ขยายให้ CMS preview และเว็บไซต์ใช้ versioned content stylesheet เดียวกัน โดยเว็บไซต์ไม่โหลด editor UI CSS หรือ editor runtime
- (capability) CAP-6 ขยายให้ custom modal action เก็บและคืน selection ก่อน dispatch command เพื่อให้คำสั่งทำงานกับตำแหน่งเดิม
- (constraint) CSS แยกเป็น editor UI stylesheet สำหรับ CMS และ content stylesheet สำหรับทั้ง CMS preview กับเว็บไซต์
- (constraint) เว็บไซต์ต้องรองรับ token class ใหม่ก่อน CMS เริ่มสร้าง HTML ที่ใช้ token นั้น และ token เดิมต้องมี alias/deprecation window จนเนื้อหาเก่าถูก migrate
- (question) Legacy inline color, font-size และ font-family จาก TinyMCE จะ map เป็น token ใด และจะจัดการค่าที่ไม่มี token ตรงกันอย่างไร?
- (question) Prefix ของ public token class เช่น `rte-` ต้องคงที่หรือให้ consumer กำหนดได้?
- (constraint) Token ID ต้องเป็น safe slug และ content CSS ต้อง scope ใต้ `.rte-content` เพื่อป้องกัน class injection และ style leakage
- (event) การตรวจ coherence หลังปรับ token/CSS contract ผ่าน: CAP-2, CAP-5 และ CAP-6 มีเกณฑ์ตรวจรับที่สอดคล้องกับ responsive token, shared content CSS และ selection-aware modal action
- (event) การตรวจ preservation หลังปรับ token/CSS contract ผ่าน: namespaced class, structural `data-*`, CSS split, responsive typography, deploy ordering, alias migration และ legacy inline-style question อยู่ครบในเอกสาร
- (direction) เพิ่ม Accessibility Checker, Source-code Editing, Custom toolbar/modal และการรองรับ SEO; Custom toolbar/modal ยังคงอยู่ใน CAP-6
- (capability) CAP-10: ตรวจปัญหา accessibility ในเนื้อหา editor พร้อมตำแหน่ง กฎ ระดับ และ optional fix โดยไม่อ้างว่าเว็บไซต์ทั้งระบบผ่านมาตรฐาน
- (capability) CAP-11: แก้ valid safe body HTML ผ่าน Source mode โดย Apply เป็น atomic undoable transaction และไม่เปลี่ยน document เมื่อ validation ล้มเหลว
- (capability) CAP-12: ตรวจ content SEO ได้แก่ heading structure, semantic HTML, image alt และ crawlable/descriptive links โดยไม่รับผิดชอบ page metadata
- (decision) Source mode รองรับ body HTML ที่ไม่เป็น executable content; ไม่รองรับ script, event-handler attribute, unsafe URL scheme, executable SVG หรือ active embed ที่ไม่ผ่าน policy
- (decision) Safe HTML ที่ visual schema ไม่รองรับต้องเก็บแบบ lossless เป็น read-only RawHtmlNode และแก้ไขผ่าน Source mode
- (decision) Document-level html/head/body/meta/title/base/link elements ไม่อยู่ใน page-content contract และ SEO metadata เป็นหน้าที่ของ CMS page
- (constraint) Source Apply ต้อง validate, parse และตรวจ policy ก่อน commit; หากมี error ให้รายงาน line/column/code และห้ามสร้าง partial state
- (constraint) Raw HTML preview ต้องไม่ execute active content; iframe/embed ที่อนุญาตต้องใช้ sandbox และ URL policy
- (decision) นำข้อค้นพบจาก review มาแก้ customization contract: token/alias validation, immutable configuration, typed dispatch result, query state, selection rules, modal lifecycle และ negative acceptance cases
- (non-goal) Visual editing สำหรับ HTML element ทุกชนิด, JavaScript execution และ page-level SEO metadata ไม่อยู่ในขอบเขต

- (question) iframe/audio/video อนุญาต host และ attribute ใดบ้าง?

- (decision) Consumer กำหนด public HTML/CSS class prefix ได้ โดยค่าเริ่มต้นเป็น `rte-`; prefix เป็น immutable configuration และการเปลี่ยนหลังมีเนื้อหาแล้วต้องผ่าน migration
